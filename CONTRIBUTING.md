# Contributing

Thanks for helping! This is a small, friendly project. The short version: open an issue for anything non-trivial
before writing a lot of code, keep pull requests focused, and make sure the checks below pass.

## Set up

Prerequisites are in the [README](README.md#build-from-source). Then:

```bash
npm install
npm run tauri:dev
```

## Before you open a pull request

```bash
npm run typecheck
npm test
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib
```

CI runs exactly these, on Linux, macOS and Windows.

## Guidelines

- **Test the logic that can be tested.** Parsers, request planning, resampling and the SQLite store are pure and have
  unit tests — new behaviour there should come with tests. UI work is checked by running the app; say in the PR
  description what you tried.
- **Keep pure logic out of components and commands.** Put it in `src/lib/` or `src-tauri/src/store/` where it can
  be tested without a window.
- **Match the surrounding code.** Comments explain *why*, not what. Prefer small functions and plain data over
  abstraction.
- **No new network calls without saying so.** This app talks only to the market-data sources listed in the README. A
  new one needs a note in the README's *Data sources* section and in the PR.
- **Dependencies.** Prefer what's already here. A new dependency needs a reason, and its licence has to be compatible
  with AGPL-3.0 distribution (add it to [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)). After any dependency change, run
  `npm run licenses` and commit the regenerated `THIRD_PARTY_LICENSES.txt`; it fails loudly if a new component ships no
  licence file and needs a look. (The release workflow regenerates it before building too.)
- **Keep Vela's attribution intact.** See [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

### App icon

The logo is a single candlestick in a green rounded tile, with the wordmark in Geist SemiBold and "Trade" in green.
Everything is generated by [`scripts/brand/build.py`](scripts/brand/build.py); change the script rather than the files:

- `assets/brand/` — the logo kit as SVG, text converted to outlines: lockups for dark and light backgrounds (the README
  uses these), a stacked version, one-color versions, the wordmark, the mark and the app icons.
- `assets/app-icon.png` — the 1024px master. The script feeds it to `npx tauri icon` for `src-tauri/icons/`, deletes the
  `android/` and `ios/` folders that creates (this is a desktop app), then redraws the sizes of 64px and under and
  `icon.ico` from thicker small-size drawings so the candle stays crisp at 16px.
- `public/favicon-32.png` and `public/favicon-128.png` — the favicon and the About dialog.

Run it with `pip install fonttools uharfbuzz cairosvg pillow` then `python3 scripts/brand/build.py` (it downloads the Geist
font from npm). Cargo doesn't notice changed icon files, so after regenerating them touch `src-tauri/build.rs` (or run
`cargo clean -p protradechart`) to make the next build embed the new icon.

### Releasing

Installed copies of ProTradeChart update themselves from the newest GitHub release, and only accept an update signed with the
updater key. `src-tauri/tauri.conf.json` holds its public half (`plugins.updater.pubkey`); the private half is **never
committed** and lives in two repository secrets, which the release workflow needs or the build fails:

- `TAURI_SIGNING_PRIVATE_KEY` — the contents of the key file;
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` — its password.

Set them with `gh secret set TAURI_SIGNING_PRIVATE_KEY < path/to/updater.key` and
`gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD < path/to/password-file`. Keep a backup of the key and its password
somewhere safe (a password manager): **if the private key is lost, installed copies can never be updated again** — users
would have to download a new build by hand — and a leaked key lets anyone push code to every install. A new pair comes
from `npx tauri signer generate -w <path>`; replacing the key means shipping one build, signed with the old key, that
carries the new public key.

To release: bump the version in `package.json`, `src-tauri/tauri.conf.json` and `src-tauri/Cargo.toml`, tag it
(`git tag v0.2.0 && git push origin v0.2.0`), review the draft release the workflow creates, and publish it. Publishing is
what makes `latest.json` visible to installed apps.

Once every platform's build has uploaded, the workflow's `checksums` job attaches the source of the AGPL components the app
is built from (`scripts/publish-component-sources.sh`: PineTS, Vela PineTS and Vela at their `package-lock.json` versions,
from the upstream tags), then downloads what the draft release actually holds and attaches a **`SHA256SUMS`** file to it (`scripts/publish-checksums.sh`, which uses `scripts/checksums.mjs`); check it is there
before you publish. It skips signatures and `latest.json`, and a re-run replaces the earlier file (re-run just that job from the
Actions page if you have to). If you also host the installers on your own site, download them from the release into a folder
and run `node scripts/checksums.mjs <folder>` to write the same file, then publish it beside them — the hashes must match the
release's, so people can compare the two.

A local `npx tauri build` that makes installers needs the key too
(`TAURI_SIGNING_PRIVATE_KEY` and `..._PASSWORD` in the environment); `--no-bundle` doesn't.

## Reporting bugs

Please include your OS, the app version (*About*), the symbol and timeframe involved, and — if it's a data problem —
whether the same symbol works on the source's own website. The app writes a log file that is very helpful to attach — Windows:
`%LOCALAPPDATA%\io.github.swapnilgitlab.protradechart\logs`, macOS: `~/Library/Logs/io.github.swapnilgitlab.protradechart`, Linux:
`~/.local/share/io.github.swapnilgitlab.protradechart/logs`. Remove anything private first.

Security issues: see [SECURITY.md](SECURITY.md) — please don't file those publicly.
